# ウォレット基盤の比較 {#wallet-infrastructure-comparison}

ウォレット基盤の選択肢は、管理権、費用構造、デプロイ作業、セキュリティの境界が異なります。
Seamsは、Cloudflareにデプロイできる、セルフホスト可能なしきい値方式の組み込みウォレットを提供します。
ここでは、基盤の管理主体と運用モデルを比較します。
Seamsは、セルフホスト可能な基盤を維持し、ホストサービスと同等のSDKと利用体験を目指します。

## 比較 {#comparison}

| モデル                    | 適したチーム                                                                                               | 主なトレードオフ                                                                                  |
| ------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| ホスト型ウォレットSaaS    | 提供者による基盤運用を求め、提供者への依存を受け入れるチーム。                                             | ウォレット構成、料金、計画が提供者に依存する。                                                    |
| セルフホストTEEウォレット | 機密計算基盤を正しく運用できるチーム。                                                                     | 安全性が、エンクレーブのイメージ、アテステーション、KMS、展開、リージョンの可用性運用に依存する。 |
| Seams SDK                 | 継続利用のユーザー・エージェント用ウォレットを作り、セルフホストのCloudflare構成を求めるプラットフォーム。 | 通常署名がMPC・しきい値方式を使うため、単一ランタイムの署名より遅延が大きい。                     |

## ホスト型ウォレットサービス {#hosted-wallet-clouds}

[Privy](https://www.privy.io/pricing)や[Dynamic](https://www.dynamic.xyz/pricing)などの提供者は、基盤運用を外部に任せたいチームに適しています。

これは製品上の利点です。同時に、次の条件を伴います。

- 本番のウォレット基盤は、提供者の境界内に留まる。
- 事業の黒字化前から、料金が固定の運用費になる場合がある。
- 移行が、提供者のエクスポート、ポリシー、アカウントモデルに依存する。
- 詳細な運用の変更が、ホストサービスの公開機能に制限される。

基盤の管理権より、提供者による運用を優先する場合に選んでください。

## セルフホストのTEE構成 {#self-hosted-tee-stacks}

信頼できる実行環境（TEE）を使うウォレットは、強いサーバー側分離を提供できます。
その環境の運用には、複雑さが加わります。

チームは、次を管理する必要があります。

- エンクレーブのイメージと再現可能なビルド。
- アテステーションのポリシー。
- KMSとの紐づけ。
- リージョンの配置。
- 展開と切り戻しの手順。
- 機密計算の提供者と、各リージョンのインスタンス全体の稼働率。

成熟した基盤・セキュリティ運用を持つチームには適しています。
デプロイ後も安全性の説明を維持するための作業は、過小評価されがちです。

## Seamsのモデル {#seams-model}

Seamsは、しきい値署名と秘匿シェアの導出を使います。
通常署名は署名シェアを生成し、単一ランタイムが本来の秘密鍵を組み立てる必要はありません。

マーケットプレイス、取引基盤、ゲーム、出金・送金製品、ステーブルコイン口座、報酬網、ショッピングウォレット、エージェント商取引に適しています。
1回の店舗決済は、通常、購入者の既存ウォレットを使い、新しいウォレットを必要としません。

Seamsは、セルフホスト可能で、サーバーレス構成に対応しやすい設計です。

- 基盤の管理権を維持し、ホストサービスと同等のウォレット体験を提供する。
- Cloudflare Workersへロールの窓口を配置し、Containers内でWallet管理のRust計算を実行する。
- Durable Objectsと、ロール別のリージョンD1へ状態を保存する。
- Worker、D1、Durable Object、Container、バックアップの使用量を把握する。
- ウォレット、セッション、署名ルート、Workerロールの分割で規模を拡大する。
- デプロイの保護を強化しても、同じウォレット構成を維持する。

## 保護の強化 {#hardening-path}

既存のランタイムアセットと開発例で、デプロイモデルを評価できます。
R122の本番セルフホスト用デプロイコンパイラーと、管理型ウォレットの移行フローは計画中です。
ランタイムのデプロイだけでは、既存ウォレットの取り込みや検証済み切り替えは実現しません。

厳密なA/B分離を保証する場合は、本番利用前に必要な管理境界を確立してください。

- Deriver AとBを、独立して管理するCloudflareアカウントへ配置する。共通管理下の別プロジェクトでは不十分。
- ロールごとに範囲を限定したデプロイ認証情報を使う。
- GitHub・Cloudflare管理者を、ハードウェアを使う多要素認証で保護する。
- Durable Objectの名前空間とロールの秘密情報を分離する。
- デプロイ手順に、承認と監査ログを加える。
- 必要に応じ、機密性の高いロールをTEEへ配置する。

## 位置づけ {#positioning}

Seamsは、分離したランタイムロールによるサーバーレス構成に対応します。
開発では、Cloudflare WorkersとDurable Objectsから始められます。
本番の保証は、実際の分離構成、バックアップの管理、リリース証跡に依存します。
テナントルートの復元とウォレットの移行は、提供状況が異なる別の機能です。

Seamsは、しきい値署名に一定の遅延を使い、単一の署名ランタイムへの依存を避け、デプロイの柔軟性を維持します。

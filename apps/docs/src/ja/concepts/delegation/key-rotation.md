# 鍵のローテーション {#key-rotation}

ローテーションには、効果が異なる複数の操作があります。変更を説明する際は、具体的な操作名を使ってください。

## 分類 {#taxonomy}

| 操作                                 | 変更内容                                                        | アドレスの変更 |
| ------------------------------------ | --------------------------------------------------------------- | -------------- |
| エンベロープの再ラッピング           | 同じ平文シェアを包む暗号化。                                    | なし           |
| テナントルートの運用シェア更新       | Deriver A/Bのシェアとエポック。有効なテナント導出ルートは固定。 | なし           |
| サーバー内部の鍵管理のローテーション | 同じ有効なサーバーシェアの保護方法。                            | なし           |
| レーンシェアの更新                   | 1つのレーンの保持者シェアとサーバーシェア。                     | なし           |
| 委任レーンの取り消し                 | レーン状態とサーバーシェアの受付。                              | なし           |
| ウォレットの鍵交換                   | ウォレットの鍵素材。                                            | 通常あり       |

Ed25519 Streaming Yaoは、署名シェアの準備・更新、SigningWorker素材の有効化、承認済みエクスポートのライフサイクル操作に参加します。
シェア自体が変わらない場合、エンベロープの再ラッピングはストレージ層で行います。
ECDSAは、別の厳密なRouter A/Bしきい値PRFの経路に従います。

## アドレスを維持する更新 {#address-preserving-refresh}

### テナントルートの運用シェア {#tenant-root-operational-shares}

各テナントには、ランダムに生成し、Deriver AとBで分担する独自のサーバー側導出ルートがあります。
更新は、有効なルートと公開コミットメントを維持しながら、2つのシェアを置き換え、エポックを進めます。
既存のECDSAアドレスとEd25519公開鍵は変わりません。
通常の署名は準備済みの署名素材を使い、この更新手順を必要としません。新しい導出手順は、一時的に停止する場合があります。

Wallet Serverは、テナントごとに直近1時間で1回の手動更新成功を許可します。
永続的な操作の再生と、サーバーが計算する再試行時刻を使います。
デプロイ環境のポリシーとダッシュボードを確認してください。
現在のダッシュボード、スケジューラー、復元機能の提供状況は、[復元と移行](/ja/deploy-and-operate/recovery-and-portability)を参照してください。

更新は、過去のコピーの破棄を証明しません。
KMSの保持境界は[テナントルートのバックアップ](/ja/deploy-and-operate/tenant-root-backups)を、有効化と中断操作の復旧は[鍵のローテーション手順](/ja/concepts/advanced/rotation-ceremonies)を参照してください。

### 署名レーンのシェア {#signing-lane-shares}

二者の加算レーンでは、次の関係が成り立ちます。

```text
h_old + s_old = wallet_key
h_new + s_new = wallet_key
delta = h_old - h_new
s_new = s_old + delta
```

公開鍵が変わらないことを確認してから、新しいレーンエポックを有効化します。

```text
H_new + S_new == 既存のウォレット公開鍵
```

取り消しは、ローテーションより優先します。
古い保持者素材が残っていても、取り消したレーンの受付は失敗する必要があります。

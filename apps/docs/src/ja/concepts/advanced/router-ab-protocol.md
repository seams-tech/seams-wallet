# Router A/Bプロトコル {#router-a-b-protocol}

Router A/Bは、各要求と応答を、参加者、操作、鍵素材へ紐づけます。
このページは、トランスクリプトの紐づけ、ロール別エンベロープ、リプレイダイジェスト、参加者識別情報、出力パッケージ、有効化記録の要件を説明します。
ロール、秘密素材の境界、操作経路については、先に[アーキテクチャ](/ja/concepts/architecture)を読んでください。

## プロトコルの不変条件 {#protocol-invariants}

1. ロールのエンベロープを復号する前に、Routerのリクエストコンテキストを紐づける。
2. Deriver AとBは、それぞれのロール専用の暗号化エンベロープを受け取る。
3. SigningWorkerの有効化を、選択したWorkerの識別情報と鍵エポックへ紐づける。
4. リプレイダイジェストと冪等性状態で、要求の再利用を防ぐ。
5. SDKが受理する前に、応答の紐づけを検証する。

Ed25519は、二者計算の境界を固定します。

1. Deriver Aは常に回路を秘匿化する側、Deriver Bは常に評価する側になる。
2. 回路、ロール割り当て、能動的安全性の方式、リクエストのグラフを、デプロイマニフェストで固定する。
3. 現在の構成は、Deriverが正しく実行することを仮定する。不正者に対して安全なOT、入力の一貫性、選択的失敗への耐性は、将来の能動的安全性構成の要件とする。
4. AとBは、1回限りの前処理チケットを使う。失敗、タイムアウト、不明状態、リプレイではチケットを消費済みにする。
5. Routerは、小さな受信者向け暗号文と公開記録を中継する。ガーブルドテーブル、ワイヤーラベル、OT状態、平文出力は扱わない。
6. 受信者は、有効化やエクスポートを受理する前に、自身の秘密シェアと公開出力の関係を検証する。

現在の保証は、悪意あるDeriverの動作、A+Bの共謀、共有アカウント管理者の侵害、基盤全体の侵害、公平性、出力配送の保証を含みません。
Routerと最大1つの悪意あるDeriverを対象とする強い構成には、別の証跡が必要です。

操作フロー、往復回数、計算モデル、デプロイ比較は、[Streaming Yao A/B](/ja/concepts/threshold-signing/streaming-yao-ab)を参照してください。

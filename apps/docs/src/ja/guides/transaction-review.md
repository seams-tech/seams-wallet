# 独自の確認コンポーネント {#custom-transaction-review}

`useSeams().wallet`の取引メソッドに`review`オブジェクトを渡すと、ウォレットでの承認前に独自のReactコンポーネントを表示できます。
ユーザーが先へ進むと、同じモーダルが独自のコンポーネントからウォレットの承認画面に切り替わります。
ユーザーに見えるダイアログは1つで、別のポップアップは開きません。
処理は、次の順序で進みます。

**独自の確認画面 → ウォレットへ進む → ウォレットで承認 → 取引の結果**

## 切り替えの仕組み {#how-the-handoff-works}

1. アプリが`review`付きで取引メソッドを呼び出します。SDKがモーダルを開き、その中に独自のコンポーネントを表示します。
   `origin`を渡すと、モーダルはアプリの要素の位置から広がります。
2. ユーザーが条件を確認します。アプリのボタンが`controls.continueToWallet()`を呼び出します。
3. モーダルは同じ枠のまま、クロスフェードでウォレットの承認画面に切り替わります。
   独自のコンポーネントの幅と左上の位置を保ち、高さだけが変わります。
   この画面は、ウォレットのiframeが呼び出し時の取引から、独自のコンポーネントの幅で表示します。ユーザーはパスキーで承認します。
4. ウォレットの承認画面の戻る矢印で、独自のコンポーネントに戻ります。
   コンポーネントのローカル状態は保持され、見積もりの期限も変わりません。

独自のコンポーネントは、署名も取引の変更もできません。ウォレットの承認画面を表示する時点を決めるだけです。
署名する取引はウォレットのオリジンが表示するため、アプリのUIに不具合があっても、ウォレットが署名する内容は変わりません。

## ホストを配置する {#mount-the-host}

`SeamsWebProvider`と、確認画面が必要とするすべてのアプリ用プロバイダーの内側に、`TransactionReviewHost`を1つ配置します。
取引を送信するコンポーネントも、このホストの内側に配置してください。

```tsx [部分的な実装例]
import { SeamsWebProvider, TransactionReviewHost } from '@seams/wallet/react';

<SeamsWebProvider config={config}>
  <TransactionReviewHost>
    <App />
  </TransactionReviewHost>
</SeamsWebProvider>;
```

確認画面は、ホストの祖先にあるコンテキストを継承します。
呼び出し元のボタンの周囲にだけ配置したプロバイダーは、確認画面にコンテキストを提供しません。

## Reactコンポーネントを渡す {#pass-a-react-component}

`render`コールバックは操作用のコントロールを受け取り、コンポーネントを返します。
返すコンポーネントでは、フック、コンテキスト、ローカル状態、`React.lazy`とSuspenseを使えます。

```tsx [部分的な実装例]
review: {
  title: 'Review purchase',
  validity: { kind: 'unbounded' },
  render: (controls) => (
    <PurchaseReview quote={quote} controls={controls} />
  ),
}
```

この例の`PurchaseReview`と`quote`は、アプリ側で用意します。
同期コールバックからJSXを返し、フックは返すコンポーネントの内側に配置してください。

ダイアログ、背景、フォーカス管理はSDKが提供します。
別のダイアログやフォーカストラップを重ねずに、内容とボタンを渡してください。

| コントロール         | 動作                                                                                                |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| `continueToWallet()` | ウォレットの承認画面を表示します。署名前に、ユーザーがその画面で承認する必要があります。            |
| `cancel()`           | 確認処理をキャンセルします。                                                                        |
| `fail(error)`        | 閉じることができるSDK標準のエラー画面を表示します。イベントハンドラーやデータ取得の失敗に使います。 |

## 確認画面のサイズを決める {#size-the-review}

確認画面のサイズがモーダルのサイズを決め、ウォレットの承認画面もその枠を保ちます。
SDKは確認画面のラッパーを測定します。測定するのは、ラッパーのレイアウト上の幅と、内容全体の高さです。
`review.className`で、そのラッパーに幅を設定してください。

```tsx [部分的な実装例]
review: {
  title: 'Review deposit',
  validity: { kind: 'unbounded' },
  className: 'deposit-review',
  render: (controls) => <DepositReview controls={controls} />,
}
```

```css [部分的な実装例]
.deposit-review {
  inline-size: 420px;
}
```

- 幅を設定しない場合、ラッパーはモーダルいっぱいに広がり、モーダルは最大の幅になります。
- 幅は280〜560 CSSピクセルの範囲で、ビューポートの幅から32ピクセルを引いた値を超えません。
- 高さは内容に合わせて、ビューポートの高さから32ピクセルを引いた値まで広がります。それより高い内容は、モーダルの中でスクロールします。
- ラッパーには、既定で0.75remの余白があります。同じクラスで変更できます。
- ウォレットの承認画面は、確認画面の幅と左上の位置を保ち、高さだけが変わります。
  ウォレットのカードは確認画面の幅で表示されるため、カードにも合う幅を選んでください。カードは約416ピクセル向けに設計されています。
  高くなったカードがビューポートからはみ出す場合だけ、モーダルは上に移動します。
- **Back to review**で戻ると、モーダルは確認画面本来のサイズに戻ります。
- ビューポートが312 × 312ピクセルより小さい場合、モーダルは周囲に16ピクセルの余白を残して、ビューポートいっぱいに表示されます。

ウォレットのカードは、どのサイズでもウォレットのiframeの中に表示されます。幅はカードのレイアウトだけを変え、表示する内容は変えません。

## 独自のモーダルから始める {#start-from-your-own-modal}

`origin` を渡すと、アプリの要素の位置から確認画面が広がります。`onVisible` を使うと、
確認画面やウォレット承認が表示された時点を取得できます。

```tsx [部分的な実装例]
review: {
  title: '入金の確認',
  validity: { kind: 'unbounded' },
  origin: amountCard.getBoundingClientRect(),
  onVisible: ({ stage, rect }) => {
    if (stage === 'review') closeAmountModal();
    trackSurface(stage, rect);
  },
  render: (controls) => <DepositReview controls={controls} />,
}
```

`origin` はビューポート基準のピクセルで指定する矩形です。SDK はメソッドの呼び出し時に一度だけ
読み取ります。最初の確認画面にだけ適用され、ウォレット承認がアプリの座標から始まることはありません。
動きを減らす設定では、確認画面はその場で表示されます。

`onVisible` は `stage` と `rect` を受け取ります。`stage` は、コンポーネントが表示されると `review`、
ウォレット承認の準備ができると `wallet` になります。「確認に戻る」でも再び `review` を通知します。
`rect` は確定した位置をビューポート基準のピクセルで示します。このコールバックのエラーは取引に影響しません。

確認画面はアプリのモーダルの上に開きます。空のページが見えるフレームを防ぐため、`onVisible` の中で
アプリのモーダルを閉じてください。そのモーダルがフォーカスを持っていた場合、削除後に SDK はフォーカスを
戻せないため、操作の終了時にアプリ側でフォーカスを移動してください。

## 有効期限を明示する {#choose-validity-explicitly}

`validity`は必須です。各呼び出しで、確認対象の取引に期限を設けるかを明示します。

- `{ kind: 'unbounded' }`：確認の期限を設けません。有効期限のある見積もりを伴わない送金などに使います。
- `{ kind: 'expires_at', atMs: quote.expiresAtMs }`：見積もりの期限を、**ミリ秒**単位のUnixタイムスタンプで渡します。
  値は正の安全な整数である必要があります。

期限切れは、承認と追加の署名を防ぎます。すでに開始した署名を取り消すことはできません。
期限切れの見積もりを更新し、新しい見積もりで新たに呼び出してください。
既存の見積もりを書き換えても、呼び出し時に取り込まれた取引は更新されません。
取引自体の経済的な条件を保証するには、コントラクトの期限とスリッページ上限を使ってください。

## 対応するメソッドと設定 {#supported-methods-and-settings}

| `useSeams().wallet`の署名者 | `review`を受け付けるメソッド                |
| --------------------------- | ------------------------------------------- |
| `near`                      | `signAndSendTransaction`                    |
| `evm`                       | `signTransaction`、`signAndSendTransaction` |
| `tempo`                     | `signTransaction`、`signAndSendTransaction` |

読み取り用のウォレット（`access: 'external'`）では、`near.prepareOwnerTransaction` が `review` を受け付けます。
確認画面は `operation.approve()` で開き、結果は型付きで返ります。詳しくは[所有者の承認](/ja/guides/application-auth)を参照してください。
この呼び出しは常にモーダルと明示的なクリックを使い、確認設定を受け取りません。

独自の確認画面には、ホストされたウォレットiframeと、実効値が`uiMode: 'modal'`、`behavior: 'requireClick'`となる確認設定が必要です。
保存済みの設定と互換性がない場合も上書きできるよう、実装例のとおり明示的に設定してください。
遅延後の自動承認には対応しません。Core SDKの呼び出し、メッセージ署名、エクスポート、認証は、このReactの確認APIを受け付けません。

SDKは、呼び出し時に取引の入力と確認設定を取り込みます。
戻り値のPromiseとライフサイクルコールバックの意味は、元のメソッドから変わりません。
「ウォレットへ進む」だけでは取引のPromiseは完了しません。呼び出しは、他のウォレット取引と同じキューに入ります。
呼び出し元やホストのキャンセル・アンマウントは、待機中または署名開始前の処理を無効にします。
署名が始まった後は、ウォレットが実際に返した結果を維持します。

## エラーとスタイル {#errors-and-styling}

NEAR は、確認のキャンセル、送信前の失敗、送信結果が不明な場合を
[取引結果](/reference/results-and-errors#signing-and-actions)で返します。
`not_submitted` の場合に保留状態を解除し、新しい確認を提示できます。
`unresolved` のハッシュは、チェーン上の結果を確認するまで保持します。
送出前に確認処理が失敗した場合、署名用コールバックは呼ばれません。

EVM と Tempo では、送出前の確認エラーは `TransactionReviewError` で reject されます。
署名と通信の失敗は、それぞれの正式なメソッドのエラー契約を維持します。

| `TransactionReviewError.code` | 意味                                                               |
| ----------------------------- | ------------------------------------------------------------------ |
| `cancelled`                   | 確認をキャンセルしました。                                         |
| `review_expired`              | 期限が切れました。再試行の前に、新しい見積もりを取得してください。 |
| `review_invalid_input`        | 確認設定または取引の入力が無効です。                               |
| `review_host_unavailable`     | 利用可能な確認ホストがありません。                                 |
| `review_owner_disposed`       | 呼び出し元またはホストを破棄しました。                             |
| `review_unsupported_mode`     | ランタイムまたは確認モードが、この確認APIに対応していません。      |
| `review_identity_changed`     | 処理中にウォレットの識別情報が変わりました。                       |
| `review_render_failed`        | 描画に失敗したか、アプリが`fail(error)`を呼び出しました。          |
| `review_prepare_timeout`      | 確認画面の読み込み、またはウォレットの準備がタイムアウトしました。 |

任意の`review.className`で、確認画面のラッパーにスタイルを適用できます。
アプリのCSSは利用できますが、ポータルによってDOMの祖先が変わります。
祖先セレクター、継承するCSS変数、CSS-in-JSの挿入先は、調整が必要な場合があります。
SDKのライト・ダークと形状のトークンは引き続き利用できます。表示内容は、アプリのCSPを満たす必要があります。

アプリ側の確認画面から開いたウォレット承認画面には、**Back to review**（確認画面に戻る）が表示されます。
戻ると、確認コンポーネントのローカル状態と、元の見積もりの期限を維持します。
再度進むと、新たな取引を送出せずに、同じ保留中の承認を再開します。
共有モーダルは、どちらの方向でも幅を保ったままクロスフェードで切り替わり、高さだけが変わります。
戻る操作は、ウォレット承認を送信するまで利用できます。取引の入力を変える場合は、新たに呼び出してください。
